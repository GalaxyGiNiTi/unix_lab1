# Лабораторная работа: Монитор Producer-Consumer

## 📋 Описание задачи

Реализация потокобезопасного монитора для синхронизации двух потоков по паттерну Producer-Consumer (Поставщик-Потребитель).

### Требования:
- **Поток-поставщик**: генерирует события каждую секунду и выводит сообщение об отправке
- **Поток-потребитель**: ожидает события и выводит сообщение об обработке
- **Синхронизация**: строгая очередность сообщений без нарушений
- **Эффективность**: ожидание с минимальным потреблением CPU (без активного ожидания)
- **Безопасность**: передача несериализуемых данных через указатели

## 🏗️ Архитектура решения

### Компоненты:

1. **Event** - структура события с несериализуемыми данными
2. **EventMonitor** - монитор с мьютексом и условной переменной
3. **Producer Thread** - генерирует события с задержкой в 1 секунду
4. **Consumer Thread** - обрабатывает события по мере их поступления

### Технологии:
- C++11 стандарт
- `std::thread` - многопоточность
- `std::mutex` - взаимное исключение
- `std::condition_variable` - эффективное ожидание
- `std::shared_ptr` - управление памятью

## 🔍 Ключевые особенности реализации

### 1. Паттерн Монитор
```cpp
class EventMonitor {
    std::mutex mutex_;              // Взаимное исключение
    std::condition_variable cond_;  // Эффективное ожидание
    bool hasEvent_;                 // Состояние буфера
    std::shared_ptr<Event> event_;  // Передаваемые данные
};
```

### 2. Отсутствие активного ожидания
Вместо `while(!condition) {}` используется:
```cpp
cond_.wait(lock, [this]() { return hasEvent_ || isShutdown_; });
```
Это переводит поток в спящее состояние с нулевым потреблением CPU.

### 3. Graceful Shutdown
Корректное завершение работы потоков через флаг `isShutdown_` и `notify_all()`.

### 4. Потокобезопасный вывод
Отдельный мьютекс для консольного вывода с временными метками.

## 📚 Теоретические основы

### Монитор
Объект синхронизации, инкапсулирующий:
- Общие данные
- Методы доступа с автоматической блокировкой
- Условные переменные для координации потоков

### Условная переменная
Механизм для эффективного ожидания изменения состояния:
- `wait()` - блокирует поток до наступления условия
- `notify_one()` - пробуждает один ожидающий поток
- `notify_all()` - пробуждает все ожидающие потоки

### Преимущества перед активным ожиданием:
| Активное ожидание | Условная переменная |
|-------------------|---------------------|
| 100% CPU | ~0% CPU |
| Энергозатратно | Энергоэффективно |
| Низкий приоритет | Быстрый отклик |

## 🎓 Выводы

Реализация демонстрирует:
1. Правильное применение паттерна Monitor в C++
2. Эффективную синхронизацию потоков без активного ожидания

4. Корректное управление жизненным циклом потоков

Важно: в реальной задаче внутри Event могут быть:

указатели,

ссылки на другие объекты,

ресурсы, которые невозможно просто так сериализовать.

Поэтому в коде события передаются через std::shared_ptr<Event> — то есть по указателю на объект.

4.2. Класс-монитор EventMonitor
class EventMonitor {
public:
    void sendEvent(std::shared_ptr<Event> ev);
    std::shared_ptr<Event> waitEvent();

private:
    std::mutex mutex_;
    std::condition_variable cond_;
    bool hasEvent_ = false;
    std::shared_ptr<Event> event_;
};


Внутри монитора:

mutex_ — обеспечивает взаимоисключающий доступ к общим данным;

cond_ — условная переменная, по которой потоки ждут/просыпаются;

hasEvent_ — флаг: есть ли сейчас событие, которое не было обработано;

event_ — указатель на текущее событие.

4.2.1. Метод sendEvent — отправка события (поставщик)
void EventMonitor::sendEvent(std::shared_ptr<Event> ev) {
    std::unique_lock<std::mutex> lock(mutex_);
        
    // Ждём, пока предыдущее событие не будет обработано
    cond_.wait(lock, [this]() { return !hasEvent_; });

    // Кладём новое событие
    event_ = ev;
    hasEvent_ = true;

    std::cout << "[Поставщик] Отправлено событие id=" << ev->id << std::endl;

    // Будим потребителя
    cond_.notify_one();
}


Логика:

Захватываем мьютекс через std::unique_lock.

Если предыдущее событие ещё не обработано (hasEvent_ == true), поток-поставщик засыпает в cond_.wait(...).

Когда флаг hasEvent_ становится false, можно положить новое событие.

Записываем указатель в event_, устанавливаем hasEvent_ = true.

Печатаем сообщение.

Вызываем notify_one(), чтобы разбудить потребителя.

Таким образом, поставщик никогда не кладёт второе событие, пока первое не обработано.

4.2.2. Метод waitEvent — ожидание события (потребитель)
std::shared_ptr<Event> EventMonitor::waitEvent() {
    std::unique_lock<std::mutex> lock(mutex_);

    // Ждём, пока событие не появится
    cond_.wait(lock, [this]() { return hasEvent_; });

    auto ev = event_;
    hasEvent_ = false;

    std::cout << "[Потребитель] Получено событие id=" << ev->id << std::endl;

    // Будим поставщика — можно отправлять следующее
    cond_.notify_one();

    return ev;
}


Логика:

Захватываем мьютекс.

Если событие ещё не пришло (hasEvent_ == false), поток-потребитель засыпает в cond_.wait(...).

Как только hasEvent_ == true, забираем указатель event_.

Сбрасываем флаг hasEvent_ = false — теперь поставщик может отправить новое событие.

Печатаем сообщение о получении.

Вызываем notify_one(), чтобы разбудить поставщика.

Возвращаем указатель на событие для дальнейшей обработки.

4.3. Потоки-поставщик и потребитель
int main() {
    EventMonitor monitor;

    const int N = 10; // количество событий

    // Поток-поставщик
    std::thread producer([&monitor]() {
        for (int i = 1; i <= N; ++i) {
            // Задержка 1 секунда
            std::this_thread::sleep_for(std::chrono::seconds(1));

            auto ev = std::make_shared<Event>(i);
            monitor.sendEvent(ev);
        }
    });

    // Поток-потребитель
    std::thread consumer([&monitor]() {
        for (int i = 1; i <= N; ++i) {
            auto ev = monitor.waitEvent();
            // Здесь можно обрабатывать ev при необходимости
        }
    });

    producer.join();
    consumer.join();

    std::cout << "Работа завершена." << std::endl;

    return 0;
}


В main() создаётся объект монитора monitor.

Создаётся два потока:

producer — раз в секунду создаёт событие Event(i) и вызывает monitor.sendEvent(...).

consumer — вызывает monitor.waitEvent() и принимает события.

Оба потока выполняют по N итераций, после чего join() дожидается завершения.

5. Очерёдность сообщений и отсутствие активного ожидания

В результате на экране появляются чётко чередующиеся сообщения:

[Поставщик] Отправлено событие id=1
[Потребитель] Получено событие id=1
[Поставщик] Отправлено событие id=2
[Потребитель] Получено событие id=2
...


Почему порядок не нарушается:

Поставщик ждёт (cond_.wait), пока предыдущее событие не будет обработано (hasEvent_ == false).

Потребитель ждёт, пока событие не появится (hasEvent_ == true).

Оба потока никогда не работают одновременно с одними и теми же данными без мьютекса.

Почему минимальная загрузка CPU:

Нет циклов while(...) { /* ничего не делаем */ }.

В ожидании используются условные переменные, потоки реально засыпают на уровне ОС.

Просыпаются только по сигналу notify_one().
